# Plan — 013-web-ui-redesign

## Summary
The server learns five new facts and exposes them additively on the existing read-only API: which calls are side calls, each call's previous call and carried/new message counts, one chip per tool call, a session digest (title, tool-state counts, errors without side calls, sources), and today's totals. The web client is then rebuilt in vanilla ES modules around a pure, Node-tested model layer (turns, context series, deltas, filters; chips are only displayed) with thin DOM components on top: Sessions list, turn timeline with rail/stats/strip/context line, and a right-side exchange drawer. No dependency, no storage change, `internal/core/` untouched.

## Context
- API: `internal/ui/api_sessions.go` (`buildSummary` is the single choke point for list, get, snapshot and live `session` events), `api_timeline.go`, `api_exchange.go`, `entries.go` (`mapEntries`), `hub.go`/`stream.go` (live), `ui.go` (`Deps`, router, embedded `web/`).
- Thread logic already exists: `internal/timeline/build.go` (`bestMatch`, `lcp`, `thread`), `sessions.go` (`SessionStats`, `preview`, `firstUserText`), `usage.go` (`CallUsage`), `harness.go` (tool states). The client profile is `internal/clients/claudecode/profile.go`, wired in `cmd/gateway/run.go` (`ui.Deps` at the UI listener and `ui.NewHub`).
- Web: `internal/ui/web/*.js|css|html`, tests `internal/ui/webtest/*.test.js` (ADR 0013), Go guards in `internal/ui/web_test.go` (no inline script/style, no HTML sinks, referenced assets embedded). Pure logic lives in `entries.js`-style modules and is imported by Node tests; components stay thin (pattern from 010).
- Build sites (CR-003): three places each rebuild a session's whole timeline and read events twice (`callFacts` through `timeline.UserTexts`, then `timeline.BuildWithUsage`): `getTimeline` (`api_timeline.go`), `getExchange` (`api_exchange.go`) and `sessionExchanges` (`hub.go`, stream snapshots and live resends). `Deps.Digests` / `DigestCache` (T016) is the pattern the timeline cache follows.
- Manual checks: `docs/manual-checks/010-hooks-ui.md`, `docs/clients/claude-code-hooks.md`, `docs/manual-checks/seed-calls.mjs`.

## Approach
Client-specific knowledge (side calls, reminders, generated title, the "Agent" tool name) is one optional interface, `ui.ClientRules`, declared in `internal/ui` and implemented by `claudecode.Profile`; `Deps.Rules` maps client name to rules (nil means prompts whole, no side calls). `timeline` stays client-agnostic: it only adds thread metadata (previous call, carried/new counts) and the tool call chip to entries. The `ui` package combines both into API fields; the browser never reads message text to classify, and never splits reminders. The browser derives everything else (turns, call numbers, stats, strip, context series, deltas, filters, key bar) in pure modules from the API fields. It never derives a chip: it displays the `chip` the server set.

## Alternatives considered
### A1 — Server annotates calls, browser builds views from pure modules (chosen)
- Pros: classification once, on the server, reusable by the CLI later (D13); view logic is Node-testable; API changes are additive.
- Cons: touches timeline, ui, claudecode and web in one feature; digest adds per-session work to list pages.

### A2 — Browser derives threads, deltas and titles from the raw entries
- Pros: no server change beyond side-call flag; one language.
- Cons: re-implements `bestMatch` and breaks the "browser never classifies" rule (AC40); a title needs response bodies the entries do not carry.

### A3 — New dedicated `/api/sessions/{id}/view` endpoint returning a prebuilt view model
- Pros: browser becomes dumb; one round trip.
- Cons: breaks the existing paged timeline and live entry events; large payload for 2,000 calls; two models to keep in sync.

## Design
**Client rules (AC3, AC37, AC40, E18, E20, E21).** `ui.ClientRules`: `IsSideCall(userTexts []string) bool` (quota probe: exactly one user message equal to `quota`; title generation: a user message starting `<session>` containing `Write the title`), `StripReminders(text) string` (removes `<system-reminder>…</system-reminder>` blocks; used for titles), `SplitReminders(text) (body string, reminders []string)` (`user_prompt` entries carry `body` and `reminders`, so the browser never reads or splits reminder text, AC16, AC40), `TitleOf(responseText) (string, bool)` (the `title` of the `{"title":…}` reply; false when empty, unparseable or errored), `IsAgentTool(name) bool`. Implemented in `internal/clients/claudecode/rules.go`; wired in `run.go`. A client without rules gets no side calls and unstripped prompts.

**Thread metadata (AC22, AC23, E6, E7).** `timeline.Entry` for an exchange/call gains `Thread` (index of the matched or new thread; server-internal), `PrevID` (request id of the earlier call in the matched thread, empty on a new thread), `Carried` and `Messages` (request message count). `timeline.NewMessages` is the one rule for the new count, used by both the timeline `call.new` and the exchange API's `new_count`: request messages not carried, plus the reply. Computed from the existing `bestMatch` result; no behaviour change to entries already produced.

**Call facts in the timeline API (AC7, AC11, AC12, AC40, E7, E8).** `model_call` entries gain `call`: `prev_id`, `side_call`, `main`, `carried`, `new`. The API sends no `n` and no `thread`: `thread` stays server-internal (`json:"-"`) and still feeds `thread_new` and `main`. The browser numbers calls when rendering: `model.js callNumbers` orders every call (all threads) by `start`, then `exchange_id` (`compareEntries`) and assigns 1-based `#n`; drawer URLs stay keyed by exchange id. `main` = thread has a user prompt and is not a side call and is not a sub-agent. A thread is a sub-agent when any tool call entry in it carries `agent_id`/`agent_type`, or its first user prompt equals the `prompt` input of a parent tool call that `IsAgentTool` names (D7). Compaction and `/clear` start threads that keep a prompt and stay main. Errored side calls stay red per call (`side_call` plus the exchange's error entry); session-level counts come from `main_errors`/`side_errors` in the digest, never recounted in the browser. Context, context partial flag and deltas are computed in the browser from the entry's `usage`, following `prev_id` back to a call with complete usage (E4, E5).

**Live resend bound (AC19, AC28).** An entry's order key is its own `start` and `exchange_id`, so a late commit does not move other calls' numbers. The stream resends a late commit's own exchange plus its direct children (calls whose `prev_id` is it): 1 + direct children, pinned for 0 to 3 children, with a grandchild and a call in another thread not resent, by `TestStream_LateCommitResendsItsDirectChildrenOnly`. In-order replay resends at most the previous call (`TestStream_ReplayOf20CallsResendsAtMostThePreviousCall`); a 21-call replay with c05 committed last resends c05 and c06 (`TestStream_LateCommitOf21CallsResendsAtMostTheNextCall`). Accepted and logged in research.md: a late call that flips a thread's `main` status resends that whole thread (read from the code, not measured, no test).

**Tool call chips (AC13, AC18, E14).** `timeline.ChipOf(state, outcome)` maps the harness verdict to one of six chips, `Chips` in display order: `ok` (asked+ran+reported, not failed), `failed` (asked+ran+reported with outcome failed), `not-run` (asked-not-run), `unmatched` (ran-not-asked-or-not-captured), `pending` (pending and ran-not-reported, an ended session too, E14), `no-hooks` (no harness data). `applyHarness` sets `Entry.Chip` on every tool call entry and on every hook entry that carries a tool call id with no matching captured call; those are always `unmatched`, in a hooks-only session too (AC18). The API exposes `chip`, with `state`, `reason` and `outcome` for the hover. For a hook-seen call, `reason` and `outcome` come from its highest hook phase (denied, succeeded or failed), live in new `Entry.HookReason` and `Entry.HookOutcome`, are mapped into the hook entry's `reason`/`outcome` JSON keys, and are display-only: they never change the chip. CLI output (`timeline.Render`, `SessionStats`, `timeline -json`) is unchanged and has no `chip`; the existing `Reason`/`Outcome` are not reused. The browser only displays: `model.js chipOf` maps a given `chip` to glyph, word and hover text, never reads `state` or `outcome` to pick a chip, and a missing chip shows as no-hooks. `TestChipOf_MapsEveryStateAndOutcome` (table over every state and outcome) pins the mapping and `TestTimelineJSON_KeySetIsPinned` pins the CLI key set.

**Session digest (AC1, AC3, AC10, AC37-AC39, E2, E3, E19, E21, E23).** `timeline.SessionDigest` (one pass, content reads only for the title) feeds `buildSummary`: `title`, `has_calls`, `has_hooks`, `tool_states` (counts of the server-set chips, all six keys present, from the same `Entry.Chip` the timeline serves: one per captured tool call and one per hook-seen tool call id, not per hook event; the Has gaps filter matches `unmatched > 0`, so a hooks-only session matches), `errors` (unchanged: all errors, so the API change stays additive), `main_errors` (side calls excluded) and `side_errors`, with `errors = main_errors + side_errors`; the UI reads only `main_errors` for the Errors column, the Has errors filter and the stats row (AC10, AC39). `usage` unchanged (side calls count). Title = latest stored generated title that `TitleOf` accepts, else first non-side user prompt with reminders stripped and not empty, cut to `PreviewRunes`, else `""` (browser shows "no prompt captured"). Because the list, get, snapshot and live `session` event all go through `buildSummary`, titles update live with no new event. CLI output (`timeline.SessionStats`) is untouched.

**Digest memo (AC1, AC3; perf).** `ui` keeps an in-memory `digestCache` mapping session id plus a version to the digest (title, tool states, error split, sources only). The version is a composite from a new read-only `store.CtxReader.SessionVersions(ids []SessionID) (map[SessionID]Version, error)`, read in one transaction from two grouped queries for a whole list page: `WITH l(p,c,k) AS (VALUES …) SELECT e.principal_id, e.client, e.session_key, COUNT(*), MAX(e.rowid), COUNT(e.parse) FROM l JOIN exchanges e ON e.principal_id=l.p AND e.client=l.c AND e.session_key=l.k GROUP BY` the three columns, and the same CTE joined to `hook_events h` with `COUNT(*), MAX(h.id)`. Query-plan evidence (sqlite3 3.46.1 CLI, read-only on the local store; the driver, modernc.org/sqlite, may differ so the test below decides): the row-value `IN (VALUES …)` form on `exchanges` plans as `SEARCH exchanges USING INDEX exchanges_principal (principal_id=?)`, which has no SCAN but walks every exchange of the principal (the whole table in a single-principal store); the CTE join plans as `SEARCH e USING INDEX exchanges_session (principal_id=? AND client=? AND session_key=?)` and `SEARCH h USING COVERING INDEX hook_events_session (…)` with only `SCAN l` for the list; a plain `session_key IN (…) AND principal_id IN (…) AND client IN (…)` uses the index too but can match identity combinations that were not requested and would need filtering back. The CTE join was chosen on that evidence and matches exact identities. Grouping and filtering use the full identity, never `session_key` alone: a session is (principal, client, key) (`sessionID`), the key is a client-supplied header value, and the same value from another principal or client is a different session, so a key-only group would merge them and share one version. A session with no exchanges (hooks only) or no hook events is absent from that query's result and gets the zero value for that half, so every requested session has a defined `Version{ExCount, ExMaxRow, Parsed, HookCount, HookMaxID}`; rows with a NULL `session_key` never match the `IN` list. A single-session read (`getSession`, live `session` events, snapshot) calls the same function with a one-element slice, so both paths run the same SQL; `TestSessionVersions_BatchEqualsSingle` proves it. Findings from the store's write paths: no single "last event seq" exists (`events.seq` is per request, `hook_events.seq` its own counter); `exchanges` is only INSERTed (no REPLACE, no DELETE anywhere), so there is no re-commit case. The normal capture path is two writes: `SaveExchange` inserts the row with `parse` NULL, then `SaveParse` (`internal/store/exchange.go`) updates `parse` and inserts all of that exchange's events in one transaction, with no change to rowid or count. `COUNT(parse)` (non-NULL parses) moves in exactly that transaction, and events are only ever inserted by it, so it covers every event write. Other writes feeding the digest: `backfill.go` sets `session_key` on old exchanges, which moves them into a session and changes its exchange count and, if they are newest, max rowid; `SaveHook` inserts into `hook_events`, which moves the hook count and max id. The composite therefore changes on all four writes (insert, parse landing, backfill, hook). A future write that edits events or exchange rows in place without changing these aggregates would be missed; `TestSessionVersions_ChangesOnEveryWritePath` (run through the batch query) is the guard and must be extended with any new write path. `TestSessionVersions_QueryPlansUseSessionIndex` runs `EXPLAIN QUERY PLAN` on the exact query strings the code runs (shared constants) through the real driver and fails unless the target table's line is a SEARCH using `exchanges_session` / `hook_events_session` with all three equality columns; any SCAN of the target table (alias or `SCAN … USING INDEX` included) or use of `exchanges_principal` fails, while `SCAN l` and constant-rows lines for the list are allowed. Cost: a list page costs two queries in total, not about two per session. Each uses the `exchanges_session` and `hook_events_session` indexes, with one row lookup per exchange for `rowid`/`parse`, so O(exchanges in the page's sessions) with no event or content reads, far below the digest's own cost (events pass plus content reads), which a hit skips entirely. `BenchmarkSessionList_WarmCache` (50-row page, every digest cached) measures the whole warm path; the implementer records the number in `research.md` Notes. Clock-dependent values (`active`, anything from `now`) and `last_at`/counts from the session row are never memoised: `buildSummary` merges the cached digest with the fresh row and `d.now()` every time. It is a pure cache: lost on restart and rebuilt on demand, so the process stays stateless in the AGENTS.md sense. `Deps` gains a shared `Digests *DigestCache`, created by `newRouter` and `newHub` when nil, because `Deps` is copied by value (list, get, snapshot and live events share one cache). Ungrouped summaries are not cached (no session version). Most of the warm list cost is the per-row `SessionStats` pass, outside the memo; `BenchmarkSessionList_WarmCache` measured about 5.6 ms (research.md Notes). Size bound: at most 512 entries, least recently used evicted; an entry holds a few hundred bytes. Concurrency: one `sync.Mutex` guards lookup and insert; compute runs outside the lock; two requests may compute the same session at once and the last write wins, which is harmless because values are immutable and equal for equal versions. Digests are stored by value and never mutated after insert, so list pages and live `session` events share it safely under `-race`. (CR-003, amends the concurrency sentence above) Digest computes now go through the per-session singleflight described in the next paragraph: concurrent requests for one (session, version) share one compute, and the compute runs on its own context so a digest that outlives its request is still stored. The rule "two requests may compute the same session at once" no longer holds.

**Timeline build cache (AC19, AC28, AC36, AC1, AC3; perf).** Measured on a 2,000-call session (research.md, "Coverage and load check"): each page did a full ~3.8 s build, a cold summary 4.83 s against the 5 s `storeTimeout`. The fix is structural, not a timeout change.
- One `buildSession(ctx, c, who, rules)` loads events once and feeds both `callFacts` (now taking the loaded events, behaviour unchanged) and `BuildWithUsage`; `getTimeline`, `getExchange` and `sessionExchanges` all call it (AC19, AC28, AC36).
- `TimelineCache` in `internal/ui`: mutex-guarded LRU keyed by session id and the `SessionVersions` key (same as the digest memo), at most 4 sessions or about 512 MB estimated retained size, whichever first. Entries (entries, facts, version, event position) are immutable and shared. Held in `Deps` as `Timelines` next to `Digests`, created when nil by `newRouter` and `newHub`. The size estimate is a documented per-build figure (marshalled entry bytes times a fixed factor), not a heap measurement. T018 measures the real retained size of a 2,000-call build and logs it in research.md Notes; over about 128 MB is logged and the task continues.
- Singleflight per session hand-written with a mutex and channels (no `golang.org/x/sync`, no new dependency), used for both digest and timeline builds. A build runs on a context derived from the server's lifetime, not the request's, so it finishes and is cached when the request times out; that request gets the usual `writeStoreErr` 504 and the retry hits the cache. `storeTimeout` stays 5 s. Server shutdown cancels builds. A failed build is not cached and is shared only by those waiting on it.
- Live sessions (AC19, AC28): per session at most one build running and one queued. A version change or live event during a build sets a dirty flag; when the build ends, exactly one follow-up build runs if dirty. While a build runs, readers get the latest cached build at once and never wait; with no cached build they wait for the first build (or time out and retry as above).
- Every timeline and summary response and the stream snapshot gains the build's `version` and `event_position` (rowid and hook id high-water marks), additive fields; no existing field changes. The stream, on open, resumes from the position in the snapshot it sent, so events between the build and the stream open are not missed (AC19).
- Paging (AC36): pages slice one cached build. The `after` token keeps its Index/Seq/Row fields (unchanged), which name a position by (start, exchange id) and not a slice index, so a token from one build resolves to the same position in a rebuilt one for entries present in both. Changes behind the cursor arrive through the stream; paged results plus stream events equal the final idle build.
- Not in 013: incremental (append-only) builds, logged as a follow-up in research.md Notes. No storage change, `internal/core/` untouched.
- `docs/manual-checks/seed-calls.mjs` and `docs/manual-checks/013-web-ui.md` state the real cause of a 504 and the real timing.

**Today (AC4, E1).** `GET /api/today?since=<RFC3339>` (the browser sends its local midnight): sessions with a call started at or after `since`, calls, and the four counters, using the existing `counterJSON` shape ("—" for unreported). New read-only `store.Reader` method for exchanges started since a time. Refetched by the client on `session` live events (debounced).

**Exchange fields for the drawer (AC21-AC25, AC29, AC40, E4, E6, E14).** `GET /exchanges/{id}` gains `side_call`, `prev_id`, `thread_new`, `messages` (`role`, cut `text`, `new`), `carried`, `new_count` (from `timeline.NewMessages`, the same rule as the timeline's `call.new`; `messages[].new` marks the reply too), `response` (`text`, `stop_reason`, assembled from stored events; empty with a reason string when not stored/parse failed), and `response_tool_call_ids` so the browser joins tool states from the loaded timeline. A section that cannot be built sets `unavailable` with a reason, never an error status.

**Web structure (AC2, AC30-AC35, AC19, AC20, AC26-AC28).** `index.html` references `style.css`, `app.js` only. New modules: `theme.js` (get/set with try/catch around localStorage, dark default, E15), `route.js` (parse/build hashes incl. `#/sessions/{id}/call/{exchangeId}`), `model.js` (chip display only: `chipOf` maps the server `chip` to glyph and text, no derivation; `callNumbers`; turns, stats, strip, context series, deltas, side-call cards; `contextPlot(entries, width)`, which takes the width and computes the plot geometry), `plot.js` (only draws that result: `contextPlotNode(plot, markId)`, an SVG polyline with a dot per main-thread call, and `fitContextPlot(plotAt, markId)`, which draws in a block at the block's own `clientWidth` and redraws through a `ResizeObserver`, so dots stay round), `filters.js` (list and timeline filters), `keys.js` (key-bar content and the shortcut reducer, input guard), `drawer-sections.js` (Request, Response, Tools, Headers; `createTimelinePage` and `createDrawer` take an optional `loadDetail`, default GET /api/exchanges/{id}), components `shell.js`, `sessions-page.js`, `timeline-page.js`, `drawer.js`. The drawer's context trend and the page's context line both call `fitContextPlot`, with the open call drawn as a larger outlined dot labelled "this call" (`contextBars` and its styles are gone). Duration-strip error bars are hatched and carry a glyph, so status does not rely on colour (AC34). `pendingBadgeShown` is removed from `entries.js`. The SVG is checked under the DOM stub only; the manual check covers it in a browser. `plot.js` spells the SVG namespace literally; `TestWeb_NoInlineOrExternalReferences` exempts exactly that quoted literal in scripts, and `TestWeb_GuardExemptsOnlyTheSVGNamespace` pins that the exemption is that one string. The guard's comment stripper keeps a `//` that follows a colon or a quote, so an absolute URL in a script is caught; a `//` after a space is still read as a comment (accepted gap, see Risks). No hidden `<svg id="svg-ns">` exists in `index.html`. `session-view.js`, `model-chip.js`, `session-list.js` are replaced; `tool-card.js` is reshaped into tool rows; `exchange-detail.js` and `ungrouped-list.js` stay, under the new shell. Opening a drawer pushes a hash; ↑/↓ replace it; Esc/close goes back (Back) when the drawer was `stacked` on an in-app open, else replaces with the session URL; a hash change within the shown session re-syncs the drawer; "all headers" goes to `#/exchanges/{id}`; focus returns to the opener or the current turn heading (E11). Live data goes through the existing `liveEffect` path; the drawer keys on request id so it holds its call, focus and scroll while content behind it updates (AC28). Auto-scroll runs only with the drawer closed and the view at the bottom. Browser retry (CR-003, AC36, AC19): `api.js getJSON` throws an error carrying the HTTP status; `showSession` retries the session summary or the first timeline page once on a 504, after about 1 s (delay injectable so tests do not wait), showing "building session…" in between; a second failure shows the error as before; later pages and other errors are not retried. The text is plain text, so `TestWeb_NoCostOrContextPercent` still holds. Rendering uses `DocumentFragment` and one build per live batch to meet the 2,000-call budget. Captured text is only set via `textContent`; the existing `web_test.go` guards stay and are extended for new files. Contrast is enforced by a Node test that reads the colour tokens from `style.css` for both themes (AC34); status never relies on colour (glyph plus word).

**Errors, tenancy, migrations.** Loopback-only and read-only as before; no storage or schema change; no new dependency. Store failures keep the existing `writeStoreErr` path.

## Risks
- Side-call and sub-agent rules are heuristics on client text: mislabel limits to a missing/extra "side calls" card; raw data and `#n` links stay. Rule lives in one profile file with table tests.
- Digest adds per-session work to every list page and live `session` event (title content reads, harness pass): one events pass, bound by the 50-row page, memoised per (session, composite version) with a 512-entry LRU bound. A stale hit would show an old title or counts, and the likeliest cause is the two-step capture (`SaveExchange` then `SaveParse` updates the row in place): the version includes the count of parsed exchanges so the parse landing changes it, backfill and hook writes are covered too, and `TestDigestCache_ParseLandingRecomputes` plus `TestSessionVersions_ChangesOnEveryWritePath` guard it. Keying on the full (principal, client, key) identity in the grouped queries keeps unrelated sessions from sharing a version. The grouped queries could degrade to a table walk if the planner picks another index (`exchanges_principal` walks a whole principal): the plan test fails on that instead of letting it slow every list page. A new write path that edits rows in place would need the version extended; a miss only costs a recompute.
- Timeline cache memory (CR-003): up to 4 immutable builds of a large session stay in memory. Bounded by 4 sessions and about 512 MB estimated; the real size of a 2,000-call build is measured and logged, and over about 128 MB is logged without stopping. The cache is lost on restart, so the process stays stateless.
- Stale serving (CR-003): readers get the previous build while a rebuild runs, so a page can lag live data by one build. Every response carries version and event position and the stream resumes from that position, so nothing is lost, only delayed until the stream delivers it.
- Live follow-up builds (CR-003): a burst of events costs at most one running and one queued build per session; a stuck build would hold the queue, so builds run on a server-lifetime context cancelled at shutdown, and a failed build is not cached.
- Hand-written singleflight is concurrency code: tests run under `-race`, and the tasks are Risk high.
- Big front-end rewrite replaces working 009/010 views: old tests are ported, not deleted, and `#/ungrouped`, `#/exchanges/{id}` keep their tests.
- Accepted limit: a late call that flips a thread's `main` status makes the stream resend that whole thread (read from the code, not measured, no test); logged in research.md.
- Accepted limit: the web guard's comment stripper reads a `//` after a space as a comment, so `" //host.example"` in a script is not caught; an absolute URL after a colon or quote is.
- Sub-agent detection (D7) can show a false turn when no hooks and no captured Agent call exist; accepted in the spec.
