# CR-001 — Plan: tool call chips are computed on the server

## Request
Update plan.md to match commits 3dc0b7c and 150baf7. Plan only; spec and ACs unchanged.

1. Chips are server-computed. The server derives one chip per tool call (state + outcome: ok / failed / not run / unmatched / pending) and exposes it as `chip`, plus the hover fields for full state, reason and hook-derived outcome. The browser only displays these and never derives a chip; remove or rewrite every mention of a browser `chipOf` deriving chips.
2. Digest `tool_states` counts those chips, once per tool call ID (not per hook event).
3. Hooks-only tools (ran-not-asked-or-not-captured) always show `? unmatched`; the hook outcome appears only in the hover. Has gaps matches these sessions.
4. CLI output is unchanged; outcome and reason are new fields, not reused existing ones.
5. Coverage table: add the cross-view chip tests (list counts = timeline chips, fixtures with a failed tool and a hooks-only session), TestChips_HooksOnlySession, and hasGapsMatchesHooksOnlySession.

Don't change T011–T016 scope beyond making their text consistent with 1–3.

## Why
A decision plus a defect found while building. The approved plan said the browser derives chips in `model.js chipOf` and the digest counts raw tool states. In practice the digest listed a failed tool as ok, and the list and timeline could disagree. Commit 3dc0b7c moved the derivation to the server (`timeline.ChipOf`, `Entry.Chip`, API field `chip`), and 150baf7 made hook-seen tools in a hooks-only session always `unmatched`, as the spec says, with the hook-derived reason and outcome carried only for the hover. The code is right and matches the spec; the plan text no longer describes it.

Flag for the human: the Request's item 1 names five chips. The approved spec and `internal/timeline/harness.go` (`Chips`, `ChipNoHooks`) have six: ok, failed, not run, unmatched, pending, no-hooks. The user was told and their text omits it, so this CR does not remove it. The plan keeps "six chips", and the digest keeps all six keys (`TestChips_*` asserts `len(tool_states) == 6`). The browser shows a missing `chip` as no-hooks.

## Plan impact
update: Summary, Approach, Design (Session digest, plus a new "Tool call chips" paragraph), Web structure, AC coverage, Test strategy. The approach (server annotates, browser displays) is unchanged, so this is not a re-plan.

Exact edits to plan.md:

1. **Summary.** Add "tool call chips" to the facts the server learns ("four new facts" becomes five). Change "pure, Node-tested model layer (turns, chips, context series, deltas, filters)" to "(turns, context series, deltas, filters; chips are only displayed)".
2. **Approach.** Last sentence: "The browser derives everything else (turns, chips, stats, …)" becomes "The browser derives everything else (turns, stats, strip, context series, deltas, filters, key bar) from the API fields. It never derives a chip: it displays the `chip` the server set."
3. **Design, new paragraph "Tool call chips (AC13, AC18, E14)".**
   - `timeline.ChipOf(state, outcome)` maps the harness verdict to one of six chips, `Chips` in display order: `ok` (asked+ran+reported, not failed), `failed` (asked+ran+reported with outcome failed), `not-run` (asked-not-run), `unmatched` (ran-not-asked-or-not-captured), `pending` (pending and ran-not-reported, an ended session too, E14), `no-hooks` (no harness data).
   - `applyHarness` sets `Entry.Chip` on every tool call entry and on every hook entry that carries a tool call id with no matching captured call. Those hook entries are always `unmatched`, in a hooks-only session too (AC18).
   - The API exposes `chip`, with `state`, `reason` and `outcome` for the hover.
   - For a hook-seen call, `reason` and `outcome` come from its highest hook phase: denied, succeeded or failed. They live in new `Entry.HookReason` and `Entry.HookOutcome` fields, are mapped into the hook entry's `reason`/`outcome` JSON keys, and are display-only. They never change the chip.
   - CLI output (`timeline.Render`, `SessionStats`) is unchanged; the new fields are not read there and the existing `Reason`/`Outcome` are not reused for hook-derived values.
   - The browser's `model.js chipOf` maps a given `chip` to glyph, word and hover text. It never reads `state` or `outcome` to pick a chip, and a missing chip shows as no-hooks.
4. **Design, Session digest.** Replace "`tool_states` (counts by the six chips, from the same harness derivation as the timeline)" with "`tool_states` (counts of the server-set chips, all six keys present, from the same `Entry.Chip` the timeline serves: one per captured tool call, and one per hook-seen tool call id, not per hook event)". The Has gaps filter matches `unmatched > 0`, so a hooks-only session matches.
5. **Web structure.** In `model.js` list, replace "chips" with "chip display (`chipOf` maps the server `chip` to glyph and text; no derivation)".
6. **AC coverage.**

   - AC6: add `filters.test.js: hasGapsMatchesHooksOnlySession`.
   - AC13: `model.js chipOf` (display only) and `timeline.ChipOf`; verified by `chips.test.js: sixChipsMapToGlyphAndText`, `hoverTitleKeepsFullStateReasonAndOutcome`, `chipIsNotDerivedFromState`, and the Go tests above.
   - AC18: add `TestChips_HooksOnlySession`.
7. **Test strategy.**
