# CR-003 — Build each session timeline once, cache it, and serve pages and live updates from the cache

## Request
Implement the answer to Q1 in research.md. (1) Load events once per build, shared by callFacts and BuildWithUsage. (2) Cache built session timelines in memory, keyed by the session version key (same as the digest memo), so pages slice one build; cap as an LRU of 4 sessions; measure and log the retained size of a 2,000-call build in research.md. (3) Singleflight per session for digest and timeline builds; a build finishes and is cached even if its request times out. Live sessions: at most one build in flight and one queued per session; events during a build mark it dirty and trigger exactly one follow-up build. While a rebuild is in flight, serve the latest cached build immediately; every response carries the build's version and event position, and the live stream resumes from exactly that position so nothing is missed. Incremental (append-only) builds are a logged follow-up, not 013. (4) Paging: the after-token is the last (start, exchange_id) returned, stable across builds; changes behind the cursor arrive via the stream. (5) Fix the seed script's 504 message and the manual-check doc's timing line. No storage change, no timeout change. Tests (behaviour, not wall-clock): idle session, 5 pages, build counter = 1; a timed-out build is cached and the retry hits it; N concurrent requests trigger one build; a burst of live events during a build causes exactly one follow-up build; a request during a rebuild gets the older build without waiting; on a live session, paged results plus stream events equal the final idle build; the LRU evicts the oldest session. Timing goes in a benchmark plus before/after pprof numbers in research.md. Add a final task whose done-condition is a fresh branch review over 80c6332..HEAD; invalidate the existing branch-review PASS so the loop cannot report it.

## Why
New information, logged in research.md under "Coverage and load check" and answered as Q1 (2026-11-03). On a 2,000-call session the server rebuilds the whole timeline on every request and cuts the page afterwards, so the browser's 5 pages do 5 full builds of about 3.8 s each (about 19.6 s in total). A cold `GET /api/sessions/{id}` costs 4.83 s (digest 3.50 s, stats 1.23 s) against the 5 s `storeTimeout`, and answers 504 on an idle gateway; the digest memo (T016) stores nothing when its compute fails, so a timed-out digest is never cached and every retry starts over. `app.js` stops opening a session when the summary fails, so the spec's 2,000-call constraint ("within 2 s of its data arriving", no cap on calls) cannot be exercised, and manual check steps 13 to 15 may not run. The profile puts 58 percent of the time in `store.Events`, read once by `callFacts` (through `timeline.UserTexts`) and again by `BuildWithUsage`.

Three build sites share the cost: `getTimeline` (`api_timeline.go`), `getExchange` (`api_exchange.go`) and `sessionExchanges` (`hub.go`, used for stream snapshots and live resends). The plan's "Digest memo" paragraph covers only the digest, so the approach has to be extended, not just patched.

The server-side build cache makes a first 504 followed by a hit on retry the normal cold path (the build finishes after the request times out), which is why the human added a bounded browser retry.

Why the Delta stays none, on a check of the AC wording: the browser retry and the "building session…" text are new visible behaviour, but they add no obligation any AC states. AC36 (show all stored history through existing paging) and AC19 describe what is shown once data arrives, and no AC or edge case says what the browser does when a session summary load fails. The retry is covered by the plan and a test. If the human wants it pinned in the spec, that would be a new AC (for example, on a 504 from the summary or first page the page shows "building session…", retries once after about 1 s, then shows the error) through a spec change; this CR does not propose it. The 2 s render constraint is unaffected: it counts from the data's arrival.

## Plan impact
update: a new Design paragraph "Timeline build cache (AC19, AC28, AC36; perf)" and edits to "Digest memo" (singleflight and detached completion), "Context" (build sites), "Web structure" (the retry in `showSession`), "Risks" (memory, stale serving, live follow-up build) and "Test strategy" and "AC coverage" (AC19, AC28, AC36, AC1, AC3). The approach stays the same (server annotates, browser builds views); this adds caching and ordering rules for how the server builds timelines, and one bounded client retry. Content:

- One `buildSession` function loads events once per build and feeds both `callFacts` and `BuildWithUsage`; `getTimeline`, `getExchange` and `sessionExchanges` all call it.
- `TimelineCache`: a mutex-guarded LRU keyed by session id and the `SessionVersions` key, bounded by 4 sessions or about 512 MB of estimated retained size, whichever first. Entries are immutable. Held in `Deps` next to `Digests` (shared, created when nil). The size estimate is a documented per-build figure (for example from the marshalled entry bytes plus a fixed factor), not a runtime measurement of the heap; the measured retained size of a 2,000-call build is logged in research.md, and over about 128 MB is logged and continues.
- Singleflight per session, for digest and timeline builds. A build runs on its own context, not the request's, so it finishes and is cached when the request times out; the request gets the usual `writeStoreErr` 504 and the retry hits the cache. The 5 s `storeTimeout` is unchanged. Server shutdown cancels builds.
- Live sessions: per session at most one build running and one queued. A version change or live event during a build sets a dirty flag; when the build ends, exactly one follow-up build runs if dirty. While a build runs, readers get the latest cached build at once and never wait; with no cached build they wait for the first.
- Every timeline and summary response, and the stream snapshot, carries the build's version and event position as new additive fields; the stream resumes from that position (rowid and hook id), so nothing between the build and the stream open is missed.
- Pages slice one cached build. The `after` token keeps its Index/Seq/Row fields, which name a position and not a slice index, so a token issued on one build resolves to the same position on a rebuilt one for entries present in both; changes behind the cursor arrive through the stream.
- Browser: `getJSON` errors carry the HTTP status. `showSession` retries the summary or the first timeline page once on a 504, after about 1 s, showing "building session…" in between; a second failure shows the error as today. Later pages and other errors are not retried. The delay is injectable so tests do not wait.
- Not in 013: incremental (append-only) builds; logged as a follow-up in research.md Notes.
- The seed script and the manual check doc state the real cause of a 504.
