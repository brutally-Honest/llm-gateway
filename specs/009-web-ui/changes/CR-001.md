# CR-001 — Rename the paging parameter cursor to after

## Request
spec AC15, AC16, AC18, AC21 and any other mention: rename the paging query parameter ?cursor= to ?after= and the response field next_cursor to next_after. Same semantics: opaque base64url keyset value, malformed value returns 400. Reason: "cursor" is a client name banned by TestCore_NoProviderOrClientIdentifiers (AC12, D10), and the purity test stays strict.

## Why
A wrong assumption: the spec and plan chose the word "cursor" for the paging key, but `internal/core/purity_test.go:14` bans the substring "cursor" (case-insensitive) in `../store`, `../timeline` and `../ui` (including `web/`). T002 (done, b2585bb) therefore fails `make verify` (8 hits in `internal/store/reader_ctx.go`, 4 in `internal/store/reader_ctx_test.go`, all `SessionCursor` / `UngroupedCursor` and comments). The purity test stays strict, so the vocabulary changes, not the test. Behaviour is unchanged; only the public name of the query parameter and response field changes.

Separate finding, not part of this delta: `internal/timeline/stats_test.go:60` (T003, STOPPED, on top of b2585bb) uses the fixture `{"type":"redacted_thinking",...}`, and `purity_test.go:34` bans "redacted_thinking". That is a T003 fixture defect (build the block type without spelling the banned literal, or change the fixture); it needs no spec change.

Also changed in spec.md as wording only (not AC lines): E1 (`next_after: null`), E4 (an `after` value from a different list), E5 ("pages with `after`"), the constraints line at spec.md:354 ("opaque `after` values") and the review note at spec.md:385. No AC is added or removed. The value stays opaque base64url over the full sort tuple; a malformed or foreign-list value is 400. The SSE resume value (`Last-Event-ID`, `?since`) is not renamed, and the historical "cursor" wording in research.md stays.

## Delta
- MODIFIED AC15 — When `GET /api/sessions?limit=&after=` is called, ... plus `next_after` (null on the last page). `limit` defaults to 50 and is capped at 200; following `next_after` lists every session exactly once. (was: `?limit=&cursor=`, `next_cursor`, "following `next_cursor`")
- MODIFIED AC16 — When `GET /api/ungrouped?limit=&after=` is called, ... with the same limit, cap and `after` rules as AC15. (was: `?limit=&cursor=` and "cursor rules")
- MODIFIED AC18 — When `GET /api/sessions/{id}/timeline?after=&limit=` is called, ... starting after the opaque `after` value (none = from the start), plus `next_after` (null when no more) and `stream_since` ... (was: `?cursor=&limit=`, "opaque `cursor`", `next_cursor`)
- MODIFIED AC21 — ... when `limit`, `after` or `since` is malformed, it shall answer 400 with code `bad_request`. (was: `limit`, `cursor` or `since`)
